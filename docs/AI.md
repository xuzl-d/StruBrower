# AI 建模助手（文本 → BIM）

用自然语言描述需求，AI 生成**结构化建模指令**，服务端逐条校验后才写入项目。
默认 **Mock 模式**（本地关键词模拟，无需 key），配置环境变量即可接入任意 OpenAI 兼容模型。

## 为什么不是“让 AI 直接吐网格”

Revit 类系统的价值在于**参数化、可编辑、可算量**。所以 LLM 只允许输出结构化指令
（标高/墙/板/柱/类型，以及造型实体的特征树），几何仍由 `src/bim/geometry.ts`、`src/bim/solid.ts` 按参数生成。这样：

- 模型输出可以被 JSON Schema + 服务端规则校验，出错不会写坏文档
- 每一步都有 rev、审计、版本快照，可撤销
- 与协作机制（WebSocket 差分/整文档广播）天然兼容

## 交互流程

```
用户在 AI 面板输入 → POST /api/projects/:id/ai/plan/stream（只读，SSE）
  → 服务端把项目摘要 + 需求发给模型 → 模型流式返回思考过程 + 工具调用参数
  → 面板实时显示：阶段提示 / 思考过程 / 输出草稿 / 特征树生成进度 / 已用时间
  → 服务端对 ops 做一次 dry-run（applyOps 只算不写）：不过就把错误回灌给模型自动改一轮
  → 结束时推送 result 事件：{ reply, ops, inspect, summary, repaired?, warning? }
  → 若 inspect 非空（模型想先看看模型）：前端转视角、截图，再把图发回模型续一轮（只续一轮）
  → 面板展示“将要执行的指令 + 数量统计”
用户点「应用到模型」→ POST /api/projects/:id/ai/apply（需要写入权限）
  → applyOps 逐条校验并生成新文档 → 保存新 rev + 审计
  → 向协作房间广播 doc 消息（其他在线成员自动同步）
  → 前端把它压入撤销栈，Ctrl/Cmd+Z 可回退
```

### 流式通道（SSE）

thinking 模型一次请求要几十秒到几分钟，一次性请求会让界面长时间空白，所以面板走
`/ai/plan/stream`，服务端把上游 SSE 事件转成下面几种事件（`data: {json}` 帧）：

| 事件 | 含义 |
| --- | --- |
| `start` | 开始（带 provider / model / images） |
| `status` | 阶段提示：连接中、正在识别图片、模型不支持工具调用正在降级… |
| `vision` | 图片识别完成：`{ model, object, parts }`（识别出的物体与零件数） |
| `reasoning` | 思考过程增量（`reasoning_content`），前端只保留尾部 6000 字 |
| `content` | 正文增量（走纯 JSON 兜底时才有） |
| `tool` | 模型决定调用 `apply_bim_ops` |
| `plan` | 工具参数累计长度，用来显示「正在生成特征树（N 字符）」 |
| `result` | 成功：`{ reply, ops, inspect, summary, ms, repaired, warning, vision }` |
| `error` | 失败：可读的错误信息 |

实现要点：

- 上游逐 token 吐帧，服务端按 100 ms 合并 `reasoning/content` 增量再推送，避免一帧一个汉字；
- 用**空闲超时**（默认 180 s 无任何字节）而不是总超时，thinking 模型可以连续思考几分钟；
- 客户端断开（点「停止」/关页面）会中止上游请求，不白烧 token；
- 非流式接口 `/ai/plan` 保留，供脚本与旧客户端使用；服务端没有流式路由时前端自动退回它。

### 工具调用与 thinking 模型的兼容

服务端请求**不强制** `tool_choice`（只声明 `tools`，让模型自己决定）：qwen3 / GLM 等 thinking 模式
会直接拒绝强制工具调用，返回 `400 Thinking mode does not support this tool_choice`。

兜底顺序，全部在 `server/ai/provider.js` 内自动完成，不需要额外配置：

1. `tools: [apply_bim_ops]`，无 `tool_choice` → 解析 `tool_calls`，或从 `content` 里的 JSON 解析；
2. 若服务端 400 且错误里带 `tool_choice` / `thinking` / `tools not supported`，或模型完全没给出可解析内容
   → 去掉 `tools` 重发一次，追加「只输出 JSON」指令，解析逻辑不变。两条路都要过 `server/ai/ops.js` 同一套校验。

### 上游异常响应（空体 / 网页 / 被截断）

`HTTP 200` 但拿不到 JSON 是网关抖动最常见的表现，处理顺序：

1. 显式 `stream:false` + `Accept: application/json`，减少上游按流式返回的概率；
2. 若返回的是 SSE（网关无视 `stream:false`），把事件流拼回一次完整 completion（含 `tool_calls` 分片）；
3. 空体 / 截断 / 429 / 5xx 自动重试一次；
4. 非流式通道两次都拿不到 JSON，且响应不是网页时，**改用流式通道再试一次**
   —— 两条通道在上游常常不是同一套实现，这是「HTTP 200 + 空响应体」最有效的兜底；
5. 返回网页（`<title>502 Bad Gateway</title>` 之类）不再重试，直接提示「baseUrl 少了 /v1、被网关拦截或鉴权页跳转」。

## 看图建模（图片 → 特征树）

AI 面板支持**上传 / 粘贴 / 拖入图片**（最多 4 张，单张 4 MB，合计 10 MB，前端会先把长边压到 1280）。

请求体多一个字段：

```json
{ "message": "照这张图建出来", "images": [{ "dataUrl": "data:image/jpeg;base64,..." }] }
```

### 为什么要两段式

主力建模模型大多是**纯文本**的：把 `image_url` 塞进去不会报错，但模型看到的只是
`[Unsupported Image]`，然后回一句「我无法查看图片」——用户会以为图没传上去。
所以 `server/ai/vision.js` 把流程拆开：

1. **视觉模型读图** → 结构化规格 JSON（物体、朝向、包围盒、零件清单、尺寸、材质色值、细节、不确定项）；
2. **建模模型**拿着这份规格 + 系统提示词的【看图建模】规则 → 一棵特征树的 `addSolid`。

规格里的尺寸是毫米，建模侧统一换算成米；`parts[].position` 描述的关系（同轴 / 嵌入 / 装在侧面）
由模型落成坐标，规则与【整机构图】一致：一个产品一棵特征树、零件重叠 ≥ 3 mm。

### 用哪个模型读图

不做任何自动挑选，规则只有四种情况：

| 情况 | 行为 |
| --- | --- |
| 主模型支持图片（网关 `/models` 的 `input_modalities` 含 `image`） | **内联直传**：图片直接进建模请求，一次调用，保真度最高 |
| 无法判断：网关没有 `/models`、清单里没有这个模型名，或**清单条目里根本没有模态字段** | 先按能读图试一次；若模型回「无法查看图片」，直接报错并提示去启用视觉模型 |
| 主模型明确不支持图片（条目里声明了 `input_modalities: ["text"]` 之类） | 用**独立视觉模型**（AI 设置里勾选后填写的那个），读图产出规格文本，再交给主模型建模 |
| 主模型不支持、且没启用独立视觉模型 | 报错：`主模型「X」不支持图片输入…请在 AI 设置勾选「独立视觉模型」` |

> 「无从判断」和「明确不支持」必须分开：cc.yjk.cn 这类网关的 `/models` 只回
> `id / object / created / owned_by / type / display_name`，一个字都不提模态。
> 早先把它当成「不支持」，导致本来能读图的 `gpt-6-astra` 被误判成纯文本、
> 传图直接报「主模型不支持图片输入」。现在这种条目返回 `null`（不知道），按能读图试。

独立视觉模型完全由用户配置，**默认不启用**：

- 模型名必须自己填（不预置、不按 id 猜、不自动挑同族模型）；
- 接口地址可选：留空复用主模型的 `baseUrl`（同厂商时最省事）；
- **API Key 独立**：单独加密存储；留空才复用主模型的 Key（同厂商可以直接留空，跨厂商必须填）。

### 规格格式（视觉模型的输出）

```json
{
  "object": "陶瓷马克杯",
  "orientation": "回转轴沿 Z",
  "bbox_mm": { "length": 90, "width": 90, "height": 105 },
  "parts": [
    { "name": "杯体", "shape": "tube", "size_mm": { "radius": 45, "height": 105, "thickness": 4 },
      "position": "底面 z=0，轴线与原点重合", "count": 1, "material": "ceramic", "color": "#F2F0EB",
      "detail": "杯口 R3 倒圆" }
  ],
  "details": ["手柄为 3/4 圆弧，截面椭圆"],
  "uncertain": ["壁厚按 4mm 估"]
}
```

`shape` 限定在内核支持的 14 种形状里（见下节），`material` 优先用 14 个预设名。

## 附带文本文件（txt / md / json / csv / 代码）

输入框左边的 **＋** 除了图片，还能收「本来就是文字」的文件：`txt / md / json / csv / tsv / log / yml / yaml / xml / ini / toml`、
常见代码扩展名（`js / ts / py / java / go / sql / sh / html / css`…）。它们不经过视觉模型，
而是作为参考资料直接拼在这一轮需求后面：

```json
{
  "message": "按附件里的房间尺寸建出来",
  "attachments": [{ "name": "room.md", "text": "客厅 6×4 米，层高 3 米；南墙开 1.8 米窗" }]
}
```

服务端（`server/ai/attachments.js`）把它拼成块，块头带序号与文件名：

```
按附件里的房间尺寸建出来

[[附件 1/1：room.md]]
客厅 6×4 米，层高 3 米；南墙开 1.8 米窗
[[/附件]]
```

- **上限**：单文件 1.2 万字、合计 2.4 万字、最多 3 个（图片另算 4 张）。超了截断并在块头标「（较长，已截断）」，
  前端也会提前提示；不设上限的话一段 10 万字的日志就能把整个上下文窗口吃光。
- **只认文本**：前端先看扩展名 / MIME，再检查开头 4 KB 有没有 NUL 或成片控制字符，二进制直接拒；
  `.step / .srp` 这类虽然也是文本，但几十万行没有阅读价值，靠体积上限挡掉。
- **落库**：附件正文随用户消息一起存进 `ai_messages.content`，所以下一轮、下次打开会话都还在；
  对话变长后由滚动摘要把它压成结论（与普通消息同一条路径）。
- **气泡只显示文件条**（文件名 + 字数，点开才展开正文）：正文是给模型看的，聊天区不该被刷成一份日志。
  前端用同一条块头规则（`[[附件 n/m：名字]]`）把历史里的块重新折起来，改格式要两边一起改。
- **用户正文仍限 4000 字**：附件不吃这 4000 的额度，但一定要有一句话（或图 / 文件）说明要做什么。

## 让 AI 看自己的成品（视口截图回灌）

模型只能凭参数想象成品，这就是早期「生成的螺丝刀不像」的根因之一。现在每次发送前，
前端会把当前三维视口截一张图（`ModelViewport` 通过 `onViewportApi` 把 `capture()` 交给 App，
`renderer.render()` 后立即 `toDataURL('image/jpeg')`，再压到长边 1024），排在用户参考图之后一起发出去，
消息里带一行 `[附：当前模型视图截图]` 说明这张图不是参考图而是它自己刚做出来的东西。

- 是否需要读图能力：`GET /api/ai/status` 返回 `canSeeImages`（主模型支持读图，或用户启用了独立视觉模型）。
  不支持时面板上的「让 AI 看当前模型」开关自动禁用，不会白白触发「模型不能读图」的报错。
- 开关默认打开，可以关掉（每次多一张图，慢一点、贵一点）。
- 截图时机会挑在**发送前**而不是应用后：那里画面已经稳定，不会拍到几何重建到一半的中间状态。
- **空场景不截**：截图会缩到 48×48 采样亮度，整张纯色（空项目 / 还没渲染出来）就当成「没有可看的东西」直接跳过 ——
  否则一次发送白烧上千 token，气泡里还会挂一张黑图。视角巡检同理，截到空白会跳过并说明。
- 气泡里只挂一个 `已附当前视图` 的小提示（带 26px 缩略图），不再占一块 88px 的大图：
  这张图是给模型看的，不是用户粘贴的参考图。截图本身**不落库**，历史消息里只留「当时附过」这一句。

## 自检闭环（agent loop）：AI 自己改、自己转视角看、不满意继续改

一句话需求 → 一次生成 → 用户自己发现「不像」→ 再来一轮，这个来回以前是用户在做。
现在做成闭环：**AI 改完立刻落地，然后自己把视图转过去截图核对，发现问题自己修，直到它认为满足需求才停**。
用户随时可以点「停止」掐断。

```
需求 ──▶ 模型给 ops / inspect / done
          │
          ├─ ops   → 立刻写入模型（不需要点确认），等几何重建
          ├─ inspect → 真转视口 + 截图，把图回灌给它
          └─ done  → 收工
          ▲                │
          └──── 下一轮 ◀────┘   （默认最多 5 步）
```

### 协议

工具参数（`server/ai/provider.js`）里一轮可以同时给三样东西：

```jsonc
{
  "reply": "机身比例偏扁，握把再往后倾 5°，顺便看一眼夹头有没有咬进握把",
  "ops": [ { "op": "editFeature", "target": "螺丝刀", "feature": "握把", "patch": { "rotate": [0, 25, 0] } } ],
  "inspect": [
    { "view": "iso" },                                        // 整机：核对整体比例
    { "view": "right", "focus": "夹头", "zoom": 2.5 }         // 特写：凑近看咬合
  ],
  "done": false
}
```

- **`ops` 与 `inspect` 可以同轮出现**，顺序固定：先应用 ops，再切视角截图。
  「改完马上看结果」写在一轮里，比拆两轮省一半时间。
- `inspect` 的视角是 `iso / front / back / left / right / top / bottom` 或 `{ azimuth, elevation }`，
  **最多 4 个**；`normalizeInspect` 会丢认得不对的项、把方位角归一化到 0–360、仰角夹到 ±88°
  （±90° 时视线与 up 平行，`lookAt` 会退化）。
- **视角不是固定几张，是 AI 自己挑的**。除了角度，它还能决定「看多近、看哪个件」：
  - `focus`：构件名、构件 id，或造型里的特征名（「夹头」「握把」「电机阵列」）。命中后取景范围从整机缩到那个件——
    布尔合并后特征没有独立网格，所以框的是它所属的构件，但配合 zoom 足够看清细节。
    匹配顺序：id → 构件全名 → 构件名包含 → 特征名包含；都没命中就退回整机（不会报错打断闭环）。
  - `zoom`：取景倍数，`1` = 框满，`2` = 推进一倍，`0.5` = 退远看整体关系。服务端夹到 `0.4–4`，
    一位小数；透视下相机不会近于包围球半径的 1/3（再近就穿进模型拍背面）。
  - label 会写成 `右视 · 聚焦「夹头」 × 2.5`，用户从截图卡片上就能看出这一张不是整机图。
- `done: true` 表示它核对完认为已满足需求，此时 ops 与 inspect 都应为空。
- 早期版本的约束「只要 inspect 非空，ops 必须为空」**已经取消**。

提示词里给了一条策略：怀疑没咬合 / 穿模 / 螺纹没做出来 / 孔位偏了 / 薄壁不对时才用特写，
而且**至少留一张整机图**核对整体比例——四张全特写会看不出「整体像不像」。

### 循环怎么走（`src/ai/agentLoop.ts`）

纯逻辑，不碰 React 也不碰 WebGL：`plan` / `apply` / `inspect` / `stopped` 都由调用方注入，
所以能在 Node 里整套跑（`scripts/agent-loop-test.ts`，52 项）。

```ts
const run = await runAgentLoop(firstRound, {
  goal,                                     // 用户需求原话，每轮复述（长循环里它会跑偏）
  plan: (round) => planStream(round),        // 一轮模型请求（流式）
  apply: (ops) => applyOps(ops),             // 立刻写进模型，返回「已应用 n 条（rev 12）」
  inspect: (views) => inspectViews(views),   // 转视角 + 截图
  stopped: () => stopRef.current,            // 用户点了停止
});
// run.reason: done | stopped | max-steps | no-action | inspect-failed | repeated
```

| 结束原因 | 含义 |
| --- | --- |
| `done` | 模型自己说核对完、已满足需求 |
| `stopped` | 用户点了停止（每轮开始、应用后、每张截图前都检查） |
| `max-steps` | 跑满 5 步还没收敛（避免无限烧 token） |
| `no-action` | 它没给 ops 也没给 inspect —— 在提问或只给建议，交回用户 |
| `inspect-failed` | 想看却一张也没截到（空场景 / 视口没渲染完） |
| `repeated` | 反复要同一组视角却什么都不改，判定为打转 |

三个防跑偏的护栏：

1. **步数上限 5**（`MAX_AGENT_STEPS`）：`≥ 3` 步时提示词会写「这是最后一步，请给出能交差的最终状态」。
2. **打转检测**：连续两轮 `inspect` 指纹相同且没有 ops → `repeated`。指纹会把 `400°` 和 `40°` 认成同一个方向。
3. **应用被拒就自己改**：`/ai/apply` 的 4xx（尺寸越界等）不中断闭环，错误原文回灌给模型，让它按提示改，
   最多重试 2 次；仍是同样的问题才停。

### 前端做的事（`AiPanel`）

- **自动应用**：footer 的「自动改并自检」默认开（记在 `localStorage`）。关掉就退化成单轮建议——只给指令，
  由用户点「应用到模型」。关掉后无法核对，所以也不循环。
- **等几何重建再拍**：`apply` 之后等两帧 + 260ms 再交回闭环。布尔合并是在 React 提交之后重建的，
  立刻截图会拍到改之前的样子，模型就会「改完说没改」。
- **相机回到原位**：巡检前记住用户的角度（`viewport.camera()`），截完再摆回去，不让人回来后找不到北。
- **停止**：进度卡片上的「停止」和发送键（运行中变成红色「停止」）都调用同一个 `cancel()`：
  先置 `stopRef` 再 `abort()`。只 abort 不够——它只掐断当前请求，下一步还会接着跑。
  `abort` 同时会掐掉服务端的上游请求（`res.on('close'` → `cancel.abort()`），不会白烧 token。
- **过程可见**：每一步是独立气泡（带「自检 2」小标），巡检截图平铺在系统消息里，
  结束后一句话交代怎么停的（`✓ 自检完成（3 步、2 次修改、3 张截图）` / `已停止（第 2 步）`）。
- **历史干净**：闭环代发的「`[自检第 2/5 步]` …」在落库时标 `internal: true`——
  它照样进上下文（模型看得到自己看过什么），但打开历史会话时不显示成用户说的话。
- **撤销基线**：闭环会连续 apply，闭包里的 `currentDocument` 会过期，撤销用的是 `docRef`（每轮更新）。

### 成本

一次闭环 = 最多 5 次模型请求 + 每次最多 4 张 1024px JPEG。比「生成一次就交差」贵，但省掉的是
用户自己看出问题、再描述一遍、再等一轮的来回。觉得贵就把「自动改并自检」关掉，或者中途点停止。

### 离屏版：同一套闭环，不依赖 WebGL

`scripts/lib/mini-render.ts` 是一个纯 CPU 的软光栅（z-buffer + 自写 PNG 编码），吃的是
`buildElementModel` 出来的同一个 `BufferGeometry` 和材质表。于是「写特征树 → 求值 → 出图 → 看图 → 改」
可以在 Node 里跑完整圈（`npm run aircraft`），不需要浏览器、不需要显卡、单张 720×480 约 1 秒：

```ts
renderSheet(geometry, materials, [
  { name: '侧视', azimuth: 90, elevation: 2, zoom: 1.42 },
  { name: '尾翼', azimuth: 88, elevation: 4, focus: [-27, 0, 11], radius: 13 },  // 任意点 + 半径的局部特写
], 'out.png', { width: 720, height: 480, columns: 2, decals });
```

它和视口版各有用处：

| | 视口截图（`inspectViews`） | 离屏渲染（`mini-render`） |
| --- | --- | --- |
| 需要的环境 | 浏览器 + WebGL + 视口已挂载 | 只有 Node |
| 取景 | 预设视角，或 `focus: 构件名` + `zoom` | 任意 `azimuth/elevation` + 任意点 `focus` + `radius` |
| 视觉保真 | 环境贴图、阴影、透明、后处理 | 只有颜色 / 粗糙度近似，没有阴影与透明 |
| 用途 | 人在环的自检闭环 | 回归测试、批量出图、离线评测 |

这也是**评测「AI 画得像不像」的地基**：给一组参考照片，让模型跑 3–5 轮闭环，最后用离屏渲染出固定视角，
既可以人看，也可以接视觉模型打「轮廓相似度」，把「像不像」变成一个可以回归的数字。

## 多轮对话与历史会话

会话不再只活在前端内存里：每条需求、每次生成的指令都落库，关掉面板、刷新页面、换设备都能接着聊。

### 单次请求的上下文怎么装

不再按「字符数拍脑袋」，而是把**模型窗口当成预算分配**（`server/ai/budget.js`）：

```
可用额度 = 窗口 - 输出预留(窗口 16%，最多 16k) - 系统提示 - 当前需求 - 图片
         ├─ 滚动摘要  ≈ 12%（最多 1600）
         ├─ 项目上下文 ≈ 42%
         └─ 历史原文   剩余全部（至少 600）
```

| 段 | 内容 | 上限 |
| --- | --- | --- |
| 系统提示 | 建模规则、材质、整机构图、看图建模 | 按实际长度计入 |
| 会话摘要 | 更早对话压成的一段技术备忘（`server/ai/memory.js`） | 预算 12%，正文本身 ≤1800 字 |
| 项目上下文 | 标高/类型/构件 + 造型实体特征树 | 预算 42%（结构化裁剪，见下） |
| 对话历史 | 从最新往前按 token 预算累积（不再固定 6 条） | 预算剩余部分；单条 ≤1500 token |

**窗口大小按模型名推断**（`contextWindowOf`）：`gemini-1.5/2` → 1M、`claude / gpt-4.1 / qwen-long` → 200k、
`deepseek / qwen3 / qwen-max / kimi` → 128k、`32k / gpt-3.5` → 32k，认不出来按 **64k** 保守处理。
私有部署或代理可以在 AI 设置里填「上下文窗口（tokens）」，或设 `STRU_AI_CONTEXT_TOKENS`（填 0 = 自动）。

**项目上下文是结构化裁剪，不是切 JSON 字符串**。早期用 `JSON.stringify(context).slice(0, 24000)`，
会切在半个括号上，模型收到残缺结构、后半段构件直接消失。现在：

1. 保留骨架（项目/单位/标高/类型/网格/统计/选中）；
2. 元素按「选中 → 造型实体 → 其它」装填；
3. 装不下时先降特征数（48 → 24 → 12 → 6），再按顺序少列构件；
4. 省略量写进 `omitted: { elements, features, note }`，模型知道「还有没列出来的」，不会凭空猜 id。

历史单条超过 1500 token 会被截断并标注；助手消息回灌时自动附一行
`[本轮指令] addSolid(电动螺丝刀)、editFeature(机身)`——历史里只存了自然语言回复，不补这一行模型
就不知道自己上一轮到底改了什么。若某段历史因预算被丢且还没进摘要，会额外插一条系统提示
「还有 N 条更早的对话未加载，涉及更早决定时先确认」，避免模型把断档当成没发生。

### 上下文压缩（两级）

| 级别 | 触发 | 做法 | 失败 |
| --- | --- | --- | --- |
| 自动（滚动摘要） | 未压缩消息 ≥ **18 条** 或 ≥ **6000 token**（谁先到算谁） | 后台把更早的一段压成结构化备忘，保留最近 6 条 / 4000 token 原文 | 静默跳过，不影响建模 |
| 手动 | 面板上的「压缩」按钮 / 点上下文占用数字 | 成块压到只剩保留窗口，每块一次模型调用（最多 2 块） | 报错给用户（点了没反应会让人以为坏了） |

摘要用固定小标题，便于后续合并时不丢关键信息：

```
【目标】【关键参数】【已完成的修改】【未决问题】【偏好】
```

「已完成的修改」要求按时间顺序，并注明被撤销/被否决的做法——否则模型会反复提同一个被否掉的方案。
摘要正文上限 1800 字，与回灌预算对齐（以前压到 4000 字却只发 2400 字，等于白花钱）。

压缩边界记在 `ai_conversations.summary_seq`：下一轮只回灌边界之后的消息。并发压缩用 in-flight
集合挡住；同一会话同时点两次「压缩」不会重复调用模型。

### 上下文可见性

`plan` / `plan/stream` 的结果带 `context`：

```jsonc
{
  "window": 128000, "tokens": 12400, "budget": 106510,
  "breakdown": { "system": 5314, "memory": 620, "project": 4200, "history": 2180, "message": 9, "images": 0 },
  "historyItems": 8, "historyDropped": 0, "compressed": 0,
  "omittedElements": 0, "omittedFeatures": 0, "featureLimit": 48
}
```

面板会话条显示 `12.4k / 128k`：超过 65% 变黄、85% 变红，鼠标悬停能看到分项与「省略了几个构件」，
点它直接压缩。打开历史会话时 `GET /api/ai/conversations/:cid` 也带一份 `usage`（纯估算、不调模型），
用户一进来就知道该不该压。

### 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/projects/:id/ai/conversations` | 会话列表（标题 / 消息数 / 最后一句 / 更新时间） |
| POST | `/api/projects/:id/ai/conversations` | 新建会话 |
| GET | `/api/ai/conversations/:cid` | 会话详情（含全部消息与当时的 ops） |
| PATCH | `/api/ai/conversations/:cid` | 重命名 |
| DELETE | `/api/ai/conversations/:cid` | 删除（需要项目写权限） |
| PATCH | `/api/ai/conversations/:cid/messages/:mid` | 回写「已应用到模型」（`applied` / `rev`） |
| POST | `/api/projects/:id/ai/conversations/:cid/compact` | 手动压缩上下文（返回 `compacted / remaining / hasMore / before / after`） |

`plan` / `plan/stream` 带 `conversationId` 时：生成前先落库这条用户需求（生成失败也留痕，
历史里能看出是一次失败尝试），结束后落库助手回复；上下文改为从库里取（摘要 + 未压缩消息），
前端传的 `history` 只在旧服务端或没有会话时生效。归属校验在开 SSE 之前做，错误照常返回 JSON。

参考图只存缩略图（长边 200px JPEG），原图几 MB 不进库。

`plan` / `plan/stream` 还接受 `attachments: [{ name, text }]`（文本附件，见上节）：服务端校验后拼在需求后面，
随用户消息一起落库；用户正文仍受 4000 字限制，附件不吃这个额度。

## 支持的指令（BIM ops）

单位米，坐标系 Z-up，平面坐标为 `[x, y]`。单次最多 60 条。

| op | 字段 | 说明 |
| --- | --- | --- |
| `addLevel` | `name`, `elevation` | 新增标高 |
| `addGrid` | `name?`, `start`, `end` | 新增轴网 |
| `addWall` | `level`, `start`, `end`, `type?`, `thickness?`, `topLevel?`, `topOffset?`, `baseOffset?`, `height?`, `name?` | 墙；未给 topLevel 时自动连到上方最近标高，没有则用 height（默认 3） |
| `addColumn` | `level`, `position`, `type?`, `width?`, `depth?`, `rotation?`, `topLevel?`, `height?` | 柱 |
| `addSlab` | `level`, `points?` 或 `rect?: {x,y,width,depth}`, `type?`, `thickness?`, `baseOffset?` | 楼板 |
| `updateElement` | `target`(id 或名称), `start?`, `end?`, `baseOffset?`, `topOffset?`, `level?`, `topLevel?`, `name?`, `visible?` | 修改单个实例 |
| `setTypeProperty` | `type`, `thickness?`, `width?`, `depth?`, `name?` | 修改类型（影响该类型全部实例） |
| `addSolid` | `library?`（模型 id）或 `features`，`params?`, `position?`, `rotation?`, `scale?`, `color?` | 任意造型（见「任意造型」一节）；`library` 取模型库里的特征树 |
| `setParams` | `target`, `params` | 改带参数模型的参数，整组联动重建（当前只有 `bracket`） |
| `setConstraints` | `target`, `dimensions?`, `formulas?`, `checks?`, `replace?` | 给任意构件写自定义约束（见「通用约束」一节） |
| `deleteElement` | `target` | 删除构件 |

示例（“建一个 6×4 米的房间”）：

```json
[
  { "op": "addWall", "level": "标高 1", "start": [0,0], "end": [6,0] },
  { "op": "addWall", "level": "标高 1", "start": [6,0], "end": [6,4] },
  { "op": "addWall", "level": "标高 1", "start": [6,4], "end": [0,4] },
  { "op": "addWall", "level": "标高 1", "start": [0,4], "end": [0,0] },
  { "op": "addSlab", "level": "标高 1", "rect": { "x": 0, "y": 0, "width": 6, "depth": 4 } }
]
```

## 任意造型（特征树）：一句话造出任意实体

除了建筑构件，AI 还能直接生成**参数化特征树**：形状 → 变换 → 阵列 → 布尔，全部由
`src/bim/solid.ts` 在渲染时求值。模型只输出 JSON —— **不写代码，也没有「生成代码 → 再编译」这一步**：

```
自然语言 → 模型返回 addSolid{features:[...]}
        → server/ai/solid.js 归一化/校验（形状白名单、尺寸与点数上限、阵列/布尔模式）
        → 特征树原样存进文档（rev +1，可撤销、可协作）
        → 前端按特征树实时求值成 CSG 实体
```

好处和 BIM 指令一致：可校验、可预览、可撤销、可协作；改一个尺寸只改那个特征的参数，
不会重写顶点、也不会重建整棵树。

如果希望**生成完之后还能调尺寸**（改柱高、改边数），用 `template` + `params` 建参数化模型，
见后面「参数化模型：生成完还能调尺寸」一节。

| op | 字段 | 说明 |
| --- | --- | --- |
| `addSolid` | `name?`, `level?`, `position?`, `baseOffset?`, `rotation?`, `scale?`, `color?`, `features[]` 或 `library` + `params?` | 用一棵特征树建造型实体（首个特征必须是 `add`）；给 `library` 则直接取模型库里的文档，见「模型库」一节 |
| `addFeature` | `target`, `feature`, `index?` | 追加一个特征：打孔、加阵列、加肋 |
| `editFeature` | `target`, `feature`, `patch` | 改某个特征的尺寸 / 位置 / 旋转 / 阵列 / 合并方式 / 材质 |
| `deleteFeature` | `target`, `feature` | 删除某个特征（基础特征不可删） |
| `updateElement` | `target`, `position?`, `rotation?`, `scale?`, `color?`, … | 造型实体同样可整体移动 / 旋转 / 缩放 / 改色 |
| `addDecal` | `name?`, `text?` 或 `image?`, `width`, `height`, `position`, `normal?`, `color?`, `background?`, `font?` | 贴花（涂装文字 / logo），见「贴花」一节 |
| `setParams` | `target`, `params` | 改带参数模型的参数，整组尺寸联动重建；静态特征树会报错 |

`target` 用构件 id 或唯一名称；`feature` 用**从 1 开始的序号**、特征 id 或唯一名称。
`position` 是 `[x, y]`（写 `[x, y, z]` 时 z 当作相对标高的抬升）；`rotation` 单位是**度**。

### 特征写法

尺寸字段与 `shape` 平铺（模型最自然会写的形态），也兼容 `shape: { shape: 'box', ... }` 的嵌套写法：

```json
{ "op": "addSolid", "name": "四翼螺旋桨无人机", "level": "标高 1",
  "features": [
    { "shape": "roundedBox", "label": "机身", "width": 0.24, "depth": 0.16, "height": 0.05, "radius": 0.012,
      "translate": [0,0,0.03], "material": "paintWhite" },
    { "shape": "tube", "label": "机臂", "radius": 0.011, "thickness": 0.002, "height": 0.21,
      "translate": [0.205,0,0.03], "rotate": [0,90,45], "material": "carbon",
      "pattern": { "type": "circular", "count": 4, "axis": "z", "angle": 360 } },
    { "shape": "group", "label": "旋翼组", "translate": [0.31,0,0.04], "rotate": [0,0,45],
      "pattern": { "type": "circular", "count": 4, "axis": "z", "angle": 360 },
      "features": [
        { "shape": "cylinder", "label": "电机", "radius": 0.019, "height": 0.034 },
        { "shape": "prism", "label": "桨叶", "profile": [[0.006,-0.004],[0.078,0],[0.006,0.004]],
          "height": 0.004, "twist": 16, "translate": [0,0,0.028],
          "pattern": { "type": "circular", "count": 2, "axis": "z" } }
      ] },
    { "shape": "cylinder", "label": "散热孔", "mode": "cut", "radius": 0.012, "height": 0.08,
      "translate": [0.04,0,0.06] }
  ] }
```

| 形状 | 尺寸字段 | 典型用途 |
| --- | --- | --- |
| `box` | `width`, `depth`, `height` | 只用于需要硬棱的方块 |
| `roundedBox` | `width`, `depth`, `height`, `radius`, `segments?` | 圆角外壳、机身、电池仓、手柄（首选） |
| `cylinder` | `radius`, `height`, `segments?` | 电机、轴、立柱 |
| `tube` | `radius`(外), `thickness`(壁厚), `height` | 空心管：机臂、支腿、导管 |
| `capsule` | `radius`, `height`(总高) | 脚垫、握把、鼻锥 |
| `sphere` | `radius` | 相机球罩、节点 |
| `ellipsoid` | `rx`, `ry`, `rz` | 整流罩、减震球、旋钮 |
| `cone` | `radius`, `topRadius`, `height` | 桨毂罩、喷嘴 |
| `torus` | `radius`, `tube` | 轮胎、卡箍、减震环 |
| `prism` | `profile:[[x,y]…]`, `height`, `twist?`, `taper?` | 任意多边形拉伸：桨叶、翼型、异形板 |
| `revolve` | `profile:[[半径,高度]…]`, `segments?`, `angle?` | 母线旋转：轮毂、花瓶、回转体 |
| `loft` | `sections:[截面…]`，截面见下 | 多截面放样：翼型桨叶、机身过渡、流线体 |
| `sweep` | `profile`, `path?:[[x,y,z]…]`, `onRoof?:{surface,…}`, `taper?:[起,止]` | 沿 3D 路径扫掠：弯管、锥形机臂、线缆；给了 `onRoof` 就跟着瓦面走 |
| `hull` | `points:[[x,y,z]…]` | 点集凸包：机头整流罩、不规则实体 |
| `tiles` | `rings:[{z,radius}…]`, `sides?`, `rows?`, `courses?`, `crown?`, `thickness?`, `lift?`, `cornerLift?`, `cornerOut?`, `board?`, `showTiles?` | **瓦面**：坡屋面上逐片铺板瓦 + 筒瓦（叠压 / 错缝 / 瓦当 / 滴水 / 角部起翘）；`board` 一并出瓦下衬板 |
| `group` | `features:[特征…]` | 子装配（整体阵列 / 变换） |

曲面（圆柱 / 圆角盒 / 放样 / 扫掠 / 旋转体）都带平滑法线；盒体类形状保留硬棱。
`segments` 缺省 32，曲面件建议 32–48。

每个特征还可以带：`label`、`mode`（`add` 合并 / `cut` 切除 / `intersect` 相交）、
`material`、`translate`、`rotate`（度）、`scale`、`pattern`
（`{type:'linear', count, step}`、`{type:'circular', count, axis?, angle?, center?}` 或
`{type:'mirror', axis?, center?}`），以及三个**曲面修饰**：`offset` / `fillet` / `shell`（见下一节）。

阵列单特征上限 **192** 个实例（原 64 → 90 个舷窗要拆 4 个特征，现在一排写完）。
注意代价：实例数是乘在几何上的，不是乘在特征数上——90 个窗切在一块板上求值约 1 秒，
再多就建议减少 `segments` 或拆成两排。

#### 曲面修饰：`fillet` / `shell` / `offset`

写在特征上，作用于**这个特征自己的几何**，顺序固定：偏移 → 倒圆 → 抽壳 → 变换 / 阵列 / 布尔。

```json
{ "shape": "box", "label": "盖板", "width": 0.32, "depth": 0.24, "height": 0.03,
  "fillet": 0.004,                                    // 棱边倒圆 4 mm
  "shell": { "thickness": 0.002, "open": "z+" },      // 抽壳 2 mm、顶面开口
  "offset": 0.001 }                                   // 先把面外扩 1 mm
```

| 修饰 | 写法 | 语义 |
| --- | --- | --- |
| `fillet` | `0.004` 或 `{ radius, segments? }` | 棱边倒圆。盒体走专用构造器（真 R 圆角），其它凸体走「内缩 r → 半径 r 的球滚一遍」 |
| `shell` | `0.002` 或 `{ thickness, open? }` | 抽壳留壁厚；`open` 取 `x+ x- y+ y- z+ z-`，数组可开多个面 |
| `offset` | `0.003`（负数为内收） | 曲面偏移：把每个面沿法向推 d，棱角处解「三面相交」得精确解 |

实现的三个要点：

1. **偏移是真的按面推**，不是按顶点法向缩放。每个顶点要同时满足「相邻各面都平移了 d」，
   这是个超定方程组，用最小二乘解（带正则项）：平面棱角上正好三面相交 → 精确；
   圆柱 / 放样这类曲面处相邻面近乎平行 → 退化成沿法向偏移，而法向偏移就是曲面的等距面。
2. **倒圆 = 内缩 r 再外扩 r**（`P ⊕ 球(r) = conv(各顶点球)`）。这个恒等式只在**凸体**上成立，
   所以非凸几何（带凹口、槽、孔）会**原样跳过**——宁可不动，也不能被滚成自己的凸包把孔填掉。
   需要给带孔件倒圆时，把 `fillet` 写在切除之前，或者对参与合并的每个零件分别给。
3. **抽壳 = 实体 − 内缩实体**；开放面是把内腔沿该方向再平移一个壁厚补切一刀，内腔正好穿出那个面，
   而其余各面的壁厚仍是 t（"直接切一个盖子"会把侧壁也削掉一截，杯口就矮了）。
   结果体积必须比原体小，否则判定 CSG 没切动、退回实心。

代价（同一台机器）：盒 / 圆柱 / 六棱柱三个形状倒圆 160 → 2,288 面（21 ms）；抽壳杯 + 管壳
17,834 面（232 ms）；`fillet` 在非凸体上一次凸性判断约 1–3 ms、然后什么都不做。

`mirror` 是**反射**而不是"复制 + 反向平移"：内核生成反射矩阵、翻转三角形绕序、法线取反，
所以镜像件的有向体积仍为正（不会被背面剔除吃掉，也不会让后续布尔算反）。
左右对称件只写一侧，`axis` 给对称面的法向（默认 `y`），`center` 给对称面上一点。

#### `loft` 的截面写法

截面可以给**参数化类型**，也可以给离散点，三者严格互斥（写两个会 400）：

```json
{ "z": 0,    "ellipse": { "rx": 2.98, "ry": 3.05, "power": 2.35 }, "offset": [-0.44, 0] }
{ "z": 12.4, "airfoil": { "chord": 8.2, "thickness": 0.13, "le": 4.3, "camber": 0.02 } }
{ "z": 20,   "profile": [[-1,0],[0,0.3],[1,0]] }
```

| 截面 | 字段 | 说明 |
| --- | --- | --- |
| `ellipse` | `rx`, `ry`, `power?` | 超椭圆。`power` 2 = 椭圆，2.2–2.6 更像机身剖面（略带方形），到 8 接近矩形 |
| `airfoil` | `chord`, `thickness?`, `le?`, `camber?` | NACA 四位翼型。`le` 是**前缘 x 坐标**（不是偏移量），弦长沿 −x 收；`thickness` 是相对厚度 0.01–0.5 |
| `profile` | `[x, y][]` | 任意闭合轮廓（6–192 点），和原来一样 |

每个截面还能带 `offset: [dx, dy]`（截面内平移，用来表达机体上翘、翼型中弧线偏移）、
`twist`（绕放样轴的扭转角，度）、`points`（重采样点数）。参数化截面会被重采样成
`points` 个点后再连面，所以**同一段放样的每个截面点数一致**，不会出现接缝。

放样方向恒为 +Z，要横着放就整体 `rotate`。例：机身「椭圆截面 + 上翘」写成
`{ z: -24, ellipse: { rx: 2.8, ry: 2.86 }, offset: [-0.16, 0] }`，省掉手算 32 个坐标。

#### 瓦面：`tiles`（古建 / 坡屋顶的瓦顶）

「在放样截面上加一圈余弦波」做不出瓦——放样出来是一条条圆脊，远看是石棉瓦。
真正的瓦顶是**一片片**铺出来的：板瓦凹、筒瓦凸、上下叠压、左右错缝、檐口有瓦当和滴水。
`tiles` 就是照这个铺法生成几何，一个特征顶几千片瓦：

```json
{ "shape": "tiles", "label": "瓦面", "material": "青瓦",
  "rings": [
    { "z": 3.00, "radius": 2.91 },   // 第一站比檐口再外挑一点 = 瓦口出檐
    { "z": 3.02, "radius": 2.72 },   // 檐口
    { "z": 3.85, "radius": 1.60 },
    { "z": 4.78, "radius": 0.10 }    // 顶点
  ],
  "sides": 6, "rows": 6, "courses": 19,
  "crown": 0.062, "thickness": 0.016, "lift": 0.02, "sag": 0.01 }
```

| 参数 | 缺省 | 说明 |
| --- | --- | --- |
| `rings` | 必填 | 屋面轮廓，从檐口到顶点逐站 `{z, radius}`，站间线性插值 = 举折曲线 |
| `sides` | 0 | 多边形边数（3–24）；**0 表示圆形屋面** |
| `rows` | 9 | 每条边（圆形为整圈）的瓦列数，也是筒瓦条数。按 ≈ 边长 / 0.32 m 估 |
| `courses` | 12 | 沿坡的瓦层数。按 ≈ 坡长 / 0.18 m 估（板瓦露 12–18 cm 才像「压六露四」） |
| `crown` | 0.05 | 筒瓦半径（直径 ≈ 10–13 cm 是官式瓦），0 = 只铺板瓦 |
| `thickness` | 0.014 | 瓦厚（板瓦薄壳的厚度，也是瓦口露出的边） |
| `lift` | 0.012 | 每片瓦下缘抬起量 = 叠压台阶。太小就只剩一条黑线 |
| `sag` | 0.012 | 板瓦横向内凹深度 |
| `margin` | 0.04 | 檐口内缩（米）。要让瓦口伸到封檐板外面就设 0，或把第一站半径给大一些 |
| `cornerLift` | 0 | **角部起翘**高度（米）。> 0 时屋面在多边形角上整体抬起来 = 翼角 |
| `cornerOut` | 0 | 角部外挑（相对半径）。和 `cornerLift` 一起决定角尖挑多远 |
| `cornerSpan` | 0.3 | 起翘的环向范围：从角到面中 0.3 对应 60% 的面宽 |
| `cornerDepth` | 0.32 | 起翘沿坡向的深度（占坡长比例） |
| `board` | 0 | **瓦下衬板（望板）厚度**（米，0–0.4）。0 = 不画 |
| `showTiles` | true | 是否铺瓦。`false` 时只出衬板，用来把望板单独做成一特征 |

生成规则（决定了它「真不真」）：

1. **按弧长分层**，不是按 z 等分。小屋面（坡长 3–4 m）按 z 分会近顶挤成一片、檐口拉得老长。
2. **错缝**：相邻两列沿坡向错开半块。真实瓦作不会把横缝对成一条直线，对齐铺出来像贴瓷砖。
   注意檐口那层只是**下沿**对齐（瓦口要齐），**上沿**照样跟着错 —— 否则檐口层和上一层之间
   会裂开半格，从上面能直接看见望板。
3. **板瓦有厚度**：顶面、底面、四条边都生成，所以瓦口有一道可见的边，不是一片纸。
4. **筒瓦分节**：每节瓦头（下端）比上端粗 7%、端面封口，一节压一节。
5. **檐口**：最下一层筒瓦套一个**实心圆盘**（整圆 + 饼厚 + 收口侧面）当**瓦当**，
   板瓦端头挂一片**有厚度的桃形舌片**当**滴水**——檐口那条起伏的花边就是它们。
   这两样都不能做成「正反两个三角」的双面片：零厚度在低角度下就是一张纸，
   一律按实体生成（前后两面 + 一圈侧壁），瓦当的圆盘下缘本来就垂到瓦口以下。
6. **翼角**：`cornerLift` / `cornerOut` 让**瓦面自己**在角上抬起并外挑（环向、坡向都按平方衰减，
   接回正常屋面时斜率为 0）。不要另做一条贴片画角 —— 平面贴片在任何角度下都是「船桨」，
   而且瓦面还是平的，翘的只有那块板。瓦当、滴水、戗脊都会自动跟着这条翘曲面走。
7. **顶点法向按翘曲后的曲面求**（中心差分），不是每个三角面各给一个平面法向。
   翼角上一片板瓦的四个角不共面，扇成两个三角面以后两面法向差 8° 上下，一面对光一面背光，
   画出来就是「一格惨白、一格灰」—— 屋面「白色错误块」就是它。逐顶点插值后是连续明暗。
   绕序也由顶点法向定，不能用「面中心 − 瓦片中心」：翼角上那个判据会把顶面判反，整片瓦变黑。
7. **望板（`board`）不是另一块曲面**：它由**瓦片同一套格子**生成（同一批 `u` 顶点、同一条 `s` 插值），
   沿法向压在瓦底之下 `sag + 4 mm`。所以它从构造上就不可能「从瓦缝里顶出来」，
   翼角抬起来时也跟着一起抬，不会在角上张嘴。**不要**再用另一个 `loft` / `revolve` 去拟合屋面：
   两块曲面的弦高差（几十毫米）足以让望板穿出瓦面。

#### 贴在瓦面上：`sweep.onRoof`（封檐板 / 戗脊 / 角梁）

写死坐标去追一条会起翘的屋面是追不上的。`sweep` 可以声明自己**跟随某个 `tiles` 特征**，
路径由那条曲面现算，屋面改了参数它自己跟着走：

```json
{ "shape": "sweep", "label": "封檐板", "profile": [[-0.045,-0.095],[0.045,-0.095],[0.045,0.065],[-0.045,0.065]],
  "onRoof": { "surface": "pv-tiles", "mode": "ring", "s": 0, "offset": -0.115, "samples": 180 } }
```

| 字段 | 缺省 | 说明 |
| --- | --- | --- |
| `surface` | 必填 | 参照的 `tiles` 特征 id（同一棵特征树内） |
| `mode` | `slope` | `slope` = 沿坡向的一条线（角上从檐口到顶点）；`ring` = 沿檐口绕一圈 |
| `u` | 0 | `slope` 用的环向参数：`0` = 多边形角上，`1/sides` = 下一个角 |
| `s` | 0.06 | `ring` 用的坡长（米，从檐口量起） |
| `range` | 全坡 | `slope` 的起止坡长 `[from, to]`（米） |
| `offset` | 0 | 沿**瓦面法向**的推距：**正 = 压在瓦面之上**（戗脊），**负 = 藏到瓦面之下**（封檐板 / 角梁） |
| `samples` | 14 | 路径采样点数 |
| `tipLift` | 0 | `slope` 时把檐口一端沿法向抬起，做翘尖；平方衰减接回 |

定位要点（这几条是「木头戳穿瓦面」的全部教训）：

- **offset 是沿法向量的，不是沿竖直方向的**。剖面坐标 `y` 在 `ring` 模式下是**向下**为正
  （平行传输标架：`binormal = tangent × normal ≈ -Z`）。要算某条边落在哪，得用
  `offset - y_up` 而不是 `offset + y_up`，符号搞反就是「封檐板从瓦口翻上来」。
- 封檐板顶边要压在 `-2 cm` 左右：再高就在翼角处翻到瓦面上方（角上屋面法向是斜的，
  竖直剖面会被「顶」出来）。
- 角梁这类实腹构件整个要藏在 `board` 之下：`offset + 剖面半高 ≤ -(board 厚 + 2 mm)`，
  并且 `range[0]` 要退到封檐板内侧，否则梁头会从封檐板里穿出去。
- 戗脊反过来：`offset ≈ +0.02` 让剖面下半埋进瓦里，只剩一道圆脊露在外面。`offset` 给到
  `0.16` 会整条悬空，从侧面能看见缝。

边界：瓦面是**贴面几何**，只往屋面上加、不参与布尔（`mode` 固定 `add`）。
望板要另起一个特征，但**仍然用 `tiles`**：`{ "shape": "tiles", "rings": …, "rows": 与瓦面相同,
"board": 0.10, "showTiles": false }`。`rows` 必须和瓦面一致，两者的横向顶点才是同一批。
举折曲线是旋转对称的，四坡顶、歇山顶这类脊线不对称的屋顶还表达不了。
实测六角亭（6 面 × 7 列 × 18 层 = 1,512 片瓦）48k 三角面、求值 86 ms。

### 材质与颜色（逐零件，`material`）

几何只决定形状，**材质决定它像不像真东西**。每个特征都可以带 `material`，渲染时按材质取值分组，
用 `geometry.groups` 做多材质渲染（`src/bim/solid.ts` 的 `buildSolidModel`）：

```json
{ "shape": "tube", "label": "机臂", "radius": 0.0115, "thickness": 0.0022, "height": 0.3, "material": "carbon" }
{ "shape": "loft", "label": "桨叶", "material": { "name": "哑光黑", "color": "#20242a", "roughness": 0.46, "metalness": 0.06 } }
```

两种写法：

| 写法 | 示例 | 说明 |
| --- | --- | --- |
| 预设名 | `"material": "aluminum"` | 服务端用 `shared/materials.js` 展开成完整参数 |
| 自定义对象 | `{ name?, color, roughness?, metalness?, opacity? }` | `color` 必须 `#rrggbb`；`roughness`/`metalness` 0–1；`opacity` 0–100 |

预设（`shared/materials.js`，界面下拉框、AI、模板共用同一份）：

| preset | 名称 | 颜色 | roughness / metalness |
| --- | --- | --- | --- |
| `aluminum` | 阳极氧化铝 | `#b9c2cb` | 0.28 / 0.92 |
| `steel` | 不锈钢 | `#cfd6dd` | 0.22 / 0.96 |
| `carbon` | 碳纤维 | `#24282e` | 0.38 / 0.18 |
| `plastic` | 工程塑料 | `#dfe4ea` | 0.55 / 0.02 |
| `plasticDark` | 深灰塑料 | `#30343a` | 0.5 / 0.03 |
| `rubber` | 橡胶 | `#1b1e22` | 0.92 / 0 |
| `glass` | 玻璃（半透） | `#cfe2ef` | 0.06 / 0.05，opacity 32 |
| `copper` / `brass` / `gold` | 紫铜 / 黄铜 / 金色镀层 | — | 0.2–0.3 / 0.95–1 |
| `paintWhite` / `paintOrange` | 白 / 橙烤漆 | — | 0.32–0.35 / 0.04–0.05 |
| `ceramic` / `wood` | 陶瓷 / 木材 | — | 0.18 / 0.7 |

规则：

- 材质挂在**特征**上，子装配（`group`）上写的材质是子特征的默认值，子特征自己写了就覆盖父级；
- 取值相同的材质自动合并成一个材质槽，40 个零件写 5 种材质 = 5 个 draw group，不会拖慢渲染；
- 没写材质的零件跟随「材质浏览器」指派的构件材质；图层/类别颜色替换优先级高于零件色（Revit 语义）；
- 改色不需要重建实体：`editFeature { target, feature: '机身', patch: { material: { color: '#20303f' } } }`，
  整体换色也可以用 `updateElement { target, color }`。

服务端校验（`server/ai/solid.js` 的 `materialSpec`）：未知预设、非十六进制颜色、`metalness`/`roughness`
越界、`opacity` ≤ 0 都会 400，并在报错里列出可用预设名 —— 模型照着改就能过。

视口侧（`src/ModelViewport.tsx`）：每个材质槽建一个 `MeshStandardMaterial`，并加了 `RoomEnvironment`
环境贴图 + ACES 色调映射 —— 没有环境反射时金属材质只能渲染成一片死黑，这是「灰模感」的另一个来源。

### 贴花（涂装 / 文字 / logo）

`addDecal` 生成的是**独立构件**（`primitive.kind: 'decal'`，`source: '贴花'`），不参与布尔、
不进特征树，所以它不会把主机体切成新面，也不会被倒圆/切孔吃掉：

```json
{ "op": "addDecal", "name": "机身标题·右", "text": "AIRBUS A350",
  "width": 8.4, "height": 0.95, "position": [3.0, 2.99, 6.55], "normal": "y", "color": "#1c3f74" }
```

| 字段 | 说明 |
| --- | --- |
| `text` 或 `image` | 二选一。`text` ≤ 120 字；`image` 必须是 `data:image/png;base64,…` 内联图（≤ 300 KB，不支持 URL） |
| `width` / `height` | 贴花实际尺寸（米），0.05–120 / 0.05–60。**比例要贴着表面**：机身标题 8.4 × 0.95 m |
| `position` | 贴花**中心点**；`[x, y]` 或 `[x, y, z]`（带 z 时按标高抬升处理） |
| `normal` | 贴哪一面、朝哪边：`x / y / z / -x / -y / -z`，默认 `y` |
| `color` / `background` / `font` | 文字色（默认 `#ffffff`）、底色（默认透明）、字体族 |

实现上是一块 `PlaneGeometry` + `CanvasTexture`：文字由 canvas 现场排版（字号随贴花宽度自适应），
材质用 `MeshBasicMaterial`（`toneMapped: false`、`depthWrite: false`、`DoubleSide`、`renderOrder = 2`），
所以**不受光照和色调映射影响**，暗部也能看清，且不会和背后的实体抢深度。

两个坑（内核已处理，写提示词时要知道）：

- 贴花默认朝 +Z、文字沿 +X。转到 ±X / ±Y 面时若只是简单转向，从外侧看会得到**镜像字**——
  `src/bim/primitives.ts` 里为每个方向单独排了旋转，`normal: 'y'` 那面要额外 `rotateZ(π)`。
- 预览里若同时画出左右两条贴花，会隔着机身看到另一侧的镜像字，所以软光栅加了背面剔除。

### 整机构图（决定成品像不像）

真实的失败案例：让模型做一把电动螺丝刀，它把「机身、握把、夹头」建成了 **6 个独立构件**，
机身给了 `220×48×48` 的方截面配 `R18` 倒圆，握把用 `capsule` 但忘了旋转。结果渲染出来是
「一根香肠上竖插着一根弹簧」—— 每个参数单看都合法，成品却完全不像。

三条硬规则（已写进 `SYSTEM_PROMPT` 的【整机构图】章节）：

1. **一个产品 = 一个构件 = 一棵特征树**。所有零件都放进同一次 `addSolid` 的 `features`，
   或后续 `addFeature` 追加到同一个 target。多个构件之间不做布尔合并，只会得到漂浮的散件。
2. **相邻零件必须真实重叠 ≥ 3 mm**。合并靠体积相交，只靠面贴合会在接缝处露黑缝。
3. **`translate` 是几何中心**，不是底端；`cylinder / tube / capsule / cone / prism / revolve`
   默认沿 Z 轴，沿 X 轴要写 `rotate: [0, 90, 0]`。

比例与圆角经验值：

- 手持件/电器外壳的截面是**扁的**：`height ≈ depth × 0.6–0.8`。写 `depth = height` 会得到一根方棒。
- `roundedBox` 的 `radius` 取 `min(width, depth)` 的 **1/8–1/6**，最多 1/3。
  `radius` 接近短边一半时整块会退化成胶囊 —— 这就是上面那个「香肠」的成因。
- 斜件（把手/支腿/手柄）不要靠 `translate` 硬凑：取根部点 P（必须在主体内部）、轴向单位向量 u，
  中心 = `P + 0.5 × 长度 × u`，`rotate` 写 `[0, θ, 0]`。后倾 20° 的握把 u = `[-0.342, 0, -0.940]`。

几何内核侧同步修了圆角盒：旧实现用单个 superellipsoid 指数近似，倒圆一大整块就变蛋形；
现在按**圆角矩形轮廓逐层放样 + 端部圆弧收缩**构造（`src/bim/solid.ts` 的 `buildRoundedBox`），
侧面是平的、只有棱边带 R，与真实 CAD 的「盒 + 棱倒圆」一致。薄板配大倒圆仍然正常：
平面轮廓保持 R，竖直方向被板厚约束成一个 1/4 圆弧。

参考实现：`shared/models/screwdriver.json` 是一棵 14 特征 / 7 材质的一体化电动螺丝刀，
同时作为提示词里的 few-shot 示例、Mock 的「螺丝刀」分支和前端「模型库」卡片。

### 复杂外形实测：一架 A350（接口边界在哪）

`scripts/aircraft-demo.ts` 复现了一张 A350 照片：机身 24 站超椭圆放样、后掠翼 + 上翘小翼（NACA
翼型）、垂尾 / 背鳍 / 平尾、旋转体短舱 + 两次布尔切孔 + 风扇 + 挂架、4 条文字贴花。指令走
**真实链路**（`applyOps` 校验 → 文档 → `buildElementModel` 求值），再由
`scripts/lib/mini-render.ts`（纯 CPU 软光栅，不需要 WebGL）出四视图 + 四张局部特写。

第一版只有 `{z, profile}` 一种截面、没有镜像、没有贴花。那一版**能出形，但特征树 61.6 KB
（18.6k token）**，模型一次写不完，只能退到低细节。随后按这三处缺口补了接口：

| 缺口 | 补法 | 效果 |
| --- | --- | --- |
| 截面只能手抄坐标 | `loft.sections[]` 支持 `ellipse{ rx, ry, power }` / `airfoil{ chord, thickness, le, camber }` / `profile`，外加 `offset`、`twist` | 机身从 22×32 个坐标（1,408 个数字）变成 24 行 `{z, ellipse, offset}`；翼型不再手推 NACA 公式 |
| 左右件要写两遍 | `pattern.type: 'mirror'`（反射矩阵 + 翻转绕序 + 法线取反，`signedVolume > 0` 断言兜底） | 机翼 / 小翼 / 平尾只写一侧，消掉「`translate` 符号写反却不报错」这类静默失败 |
| 没有涂装 | `addDecal` 指令 → 独立 `primitive.kind: 'decal'` 构件（`CanvasTexture` + `MeshBasicMaterial`，不参与布尔） | `AIRBUS A350` / `A350` 直接给文字、宽高、法向即可 |

补完后的体积（`diagnostics/aircraft/index.html` 有对照图和完整清单）：

| | 高细节 | 低细节 |
| --- | --- | --- |
| 特征 / 三角面 | 23 + 4 贴花 / 12,503 | 16 / 7,815 |
| 特征树体积 | 9.7 KB（642 个数字，≈2.9k token） | 6.6 KB（446 个数字，≈2.0k token） |
| `applyOps` / 求值 | 2 ms / 96 ms | 2 ms / 35 ms |

同一架飞机，**61.6 KB → 9.7 KB（18.6k → 2.9k token）**，从"一次写不完"变成"一次写得完还留余量"。
关键不在压缩，而在于把「几何求值」从模型转移给内核：模型只写"这一站是椭圆、rx 2.98 ry 3.05、
上翘 0.44 m"，坐标由内核算。

第二轮又补了四处（细节见上一节的「曲面修饰」）：

| 缺口 | 补法 | 现在能做什么 |
| --- | --- | --- |
| 没有倒圆 / 抽壳 | 特征级 `fillet` / `shell` / `offset` | 台基、额枋、檐口板、杯、管壳、箱体都能一次写出来；亭子直接受益 |
| 曲面不能偏移 | `offset`（面平面最小二乘求解） | 均匀加厚 / 让位；薄壳件不再靠"外壳 + 内壳 + 布尔减" |
| 阵列单段 64 | 上限提到 **192** | 一排 90 个舷窗写在同一个特征里（代价：求值约 1 秒） |

仍有边界的（不影响接口可用性，属"再往下要做内核"的部分）：

1. **倒圆只对凸体成立。** 带凹口 / 槽 / 孔的非凸件会被跳过（内核不会毁形，但也不会偷偷近似）。
   融合式翼梢、垂尾根部的变半径整流罩仍然做不到——那需要 B-rep 级的曲面圆角，不是滚球能替代的。
2. **没有 2D 轮廓倒圆。** 凹多边形 `prism` 的平面角只能靠手写 `profile` 点或改用 `roundedBox`。
3. **没有贴图材质**，只有独立平面的贴花 → 蒙皮分缝、铆钉排、真实涂装分界线仍做不出来。
4. **布尔之后没有倒角。** `fillet` 作用在特征自己的几何上，切出来的新棱是尖的；
   要圆就得把 `fillet` 写在切除之前，或者对切除结果单独建一个特征。

顺带一提，垂尾"像不像"主要是**参数怎么摆**的问题，不是接口问题：第一版按"前缘直线 + 弦长递减"
写，后缘就前倾成三角形；改成「后缘钉在竖直面 `x = -28.8`、弦长从 10 m 收到 3 m」，前缘自然得到
33° 后掠，一下就像了。

### 模型库：案例模型是特征树数据，不是代码

每件案例都是 `shared/models/<id>.json` 里的一份**特征树文档**，和 AI 通过 `addSolid.features`
发出来的是同一种东西：

```json
{ "id": "pavilion-hex", "name": "六角攒尖亭", "summary": "…",
  "features": [ { "id": "pv-base", "label": "台基", "shape": { "shape": "prism", "profile": [[2.78, 0], …] } }, … ] }
```

`shared/library.js` 是唯一读取入口（结构校验 → 冻结 → 深拷贝给调用方），
`src/bim/solidTemplates.ts` 只把它翻成界面用的清单。**内核里没有一根柱子、一片瓦是为亭子写的**：
`prism / cone / loft / sweep / tiles / revolve / group / pattern` 全是通用形状。

为什么要把生成器删掉：

- 生成器写进源码之后，模型只有改代码的人能改，AI 既看不见也改不了；
- 数据化之后，设计库、离线出图（`npm run pavilion` / `npm run aircraft`）、AI 的 few-shot
  引用**同一份文件**，不存在「模板一个样、AI 生成另一个样」；
- 新增模型 = 新增一份 JSON（或让 AI 用 addSolid 拼出来再存），不动 TypeScript；
- 模型怎么拼的，AI 读 JSON 就学会了——这比读一段 JS 便宜也准确。

| 入口 | 路径 | 适用 |
| --- | --- | --- |
| 模型库 | 功能区「造型」页 → **模型库** → 选卡片 → 放置到当前标高 | 新建造型 |
| 造型编辑器 | 选中造型构件 → 属性面板 → 编辑造型 → 顶部「模型」下拉 | 替换已有构件的特征树 |
| AI | `addSolid { library: 'pavilion-hex' }` | 引用现成案例，再 `editFeature` 改尺寸 |

| 模型 | 文件 | 组成 | 要点 |
| --- | --- | --- | --- |
| A350 客机（1:10） | `aircraft-a350.json` | 1 个顶层 `group`（整棵 19+ 特征在组里，根 `scale` 0.1） | 超椭圆放样 + 翼型后掠翼 + 镜像 + 短舱切孔 |

古建亭值得单独记几笔（这些是当初排数据时踩出来的，改 JSON 时同样适用）：

1. **攒尖顶 = 正多边形截面沿 z 放样，半径按坡度角积分收。** 檐口 21°、脊部 62°，越往上越陡；
   只有一个幂函数（`r = R(1−t)^1.25`）时整片屋面会一起收，看不出「举折」。放样 23 个截面
   （8 个在逆光下能看出折线）。
2. **瓦面交给 `tiles`，别在截面上做文章。** 给放样截面加余弦起伏只能做出圆脊，近看没有一片瓦。
   现在是望板（`tiles` + `board`，不铺瓦）+ 瓦面（`tiles`）两层，用同一套曲面：板瓦横向内凹、
   列缝压筒瓦、层层叠压 20 mm、相邻列错缝半块、檐口瓦当 + 滴水。代价 48k 三角面 / 90 ms，
   换来能数清瓦片。
3. **屋面要是壳，不是实心锥。** 望板就是一块 10 cm 的衬板（`board`），屋面天然是薄壳，
   不用再挖内腔；亭内抬头能看见雷公柱与 6 根由戗。（别用 `shell`：屋面内凹，法向偏移会自交。）
4. **翼角是瓦面自己翘**（`tiles.cornerLift / cornerOut`），不是另外贴一块板。
   贴片在任何角度下都是「船桨」，而且瓦面还是平的；`cornerLift` / `cornerOut` 让板瓦、筒瓦、
   瓦当、滴水一起跟着翘曲面走，戗脊再复现同一条衰减曲线（`(1 − s/depth)²`）压在棱线上。
5. **斗拱要露出来，檐口就得抬高**（斗拱层 0.4 m 写进 `pv-dougong` 的位置与 `eaveZ`）；
   而且斗拱必须排在屋腔 `cut` 之后——`cut` 切的是「已有零件」，先加会被自己家的屋腔吃掉。
6. **封檐板要克制**：它是给壳封边的竖板，角部只抬 6 cm；板翘而屋面不翘，中间必然裂一道缝。

三个通用坑：`prism` 是**居中**拉伸（台基忘了抬 h/2 会埋进地里）；按边布置时局部 **+Y 指向圆心**；
`group` 的 `scale` 在 rotate/translate **之前**生效，抬升量要按缩放后的尺寸给。

履带吊（机械类）的几条做法，换别的机器同样成立：

1. **先量、再建。** 拿到 STEP / OBJ 参考件别凭印象定尺寸：把顶点按「两条履带质心连线」旋到车体坐标
   （X 沿履带、Y 横向、地面 z=0），再统计各组件包围盒。这台车量出来是履带 5.06 × 0.66 × 1.25、
   轨距 2.79、车架 4.76 × 3.33 × 0.94、驾驶室 1.84 × 1.07 × 1.59 —— 有这四组数，整车比例就不会「像玩具」。
2. **环状构件用「闭合 `sweep`」**：履带环 = stadium 中线（两段直线 + 两端半圆，21 个点）+ 矩形剖面，
   `closed: true`。路径**首尾不要给重复点** —— 重合点算出来是零长度切线，那一段会翻面。
   剖面 x 落在**横向**、y 落在**径向**（平行传输标架），所以剖面写成 `[宽, 厚]` 就对了。
3. **履带要「像履带」，靠三件东西**：① 履带齿（横条）长在**履带环外表面之外** —— 下排贴地、上排朝上、
   两端沿半径外扩，26 个特征就够铺一圈；齿长在环里（半径写小）会被环整个吞掉，渲染出来是一条光板。
   ② 履带架用**白色分段侧板**（3 段 `prism` + 12 mm 错台），比一根黑梁像机器一百倍。
   ③ 端部轮盘做**一圈螺栓孔**（18 个小圆柱做 `circular` 阵列）+ 下缘一排支重轮端盖（圆头凸出侧板）。
   这三个细节比履带板本身的形状更影响「像不像」。
4. **箱型臂用一个 `prism` 就够**：圆角矩形轮廓 + `taper` 0.60 直接得到锥形臂身，
   再叠两处黑色节套（同轮廓按 `boomScale(z)` 放大 3%）就是伸缩臂的节间带。
   比「若干节圆角盒串起来」省特征，也不会在节间露缝。
5. **任意方向的杆用「两点路径 sweep + 圆剖面」**：变幅缸筒、活塞杆、钢丝绳、吊钩全是这个写法。
   比按轴向算欧拉角稳，也不用管三种旋转的先后顺序。液压缸这样分段：缸筒占 58% 长度（粗、深色）+
   活塞杆收到臂上的铰点（细、镀铬）；上铰点用 `boomWorld()` 反算，改仰角时自动跟着走。
6. **臂头别做成实心盒子**：实心盒子从侧面看是块空白板，从前面看只剩三条缝。做开放式框架 ——
   四根立柱 + 顶底横梁 + 三只滑轮 + 滑轮轴，轮缘才露得出来。
7. **车身曲面用 `loft`，不要用 `roundedBox` 拼**：每层给一条圆角矩形平面轮廓（从后缘中点起、朝 −y 走，
   各层起点必须一致，否则放样会拧），前端按 `xf(z)` 幂曲线后收就得到斜切车头，顶部再铺 12 层
   R≈0.4 的圆弧内缩就得到冲压件那种圆肩。`roundedBox` 出来的是一块「肥皂」，斜切只能用 `hull`/`loft`。
   `loft` 两端会自动封盖，顶盖与侧壁法向不共享 = 顶面边缘是硬边（想要柔边就把圆角铺到切线水平）。
   **倾角要照侧影量，不能照面法向**：这台车前脸的面法向只读出 27°，但侧影（|y|>0.7 采样）从
   z=1.57 的 x=1.28 一路退到 z=2.55 的 x=0.50，后倾 38° —— 圆角半径把侧面往前“拉”，
   眼睛认的是这条轮廓线。第一版只做 16° 的幂曲线，渲染出来仍旧是方块；改成
   `xf(z)=1.29−0.71·u^0.95`（u 从 0 到 1）才和参考件逐层对上（各 z 分带误差 ≤0.14 m）。
   同理，**贴在曲面上的细带（腰线、饰条）也要用两层 `loft`**：竖直 `prism` 拉 50 mm，在 33° 斜面上
   两端会翘出十几毫米的“小翅”，正侧影一看就露。
8. **驾驶室的「镂空」只能靠几何，不能靠材质**：`mini-render` 完全不读 `opacity`/`transparent`
   （grep 为空），所以整块玻璃壳 = 一坨不透明塑料。正确做法是**骨架 + 窗洞 + 内装**三件套：
   深色骨架用 5 道横框（底裙 / 下围 / 腰梁 / 窗楣 / 顶盖，都是两层 `loft` 贴轮廓）+ 3 组立柱
   围出窗洞；窗洞里**留空**（侧窗做成下格固定玻璃 + 上格敞开），再往里塞座椅、操纵台、操纵杆 ——
   没有内装的窗洞是黑洞，比实心壳更糟。外侧防护网要**悬挑 60–70 mm** 挂在窗外并带四边框，
   贴着玻璃放会读成「窗上的贴纸」。玻璃在离屏图里按明度取色（骨架 `#3a434c` / 玻璃 `#546b78`），
   深过骨架就分不出窗了。
9. **`roundedBox` 的 `radius` 受 `min(width, depth)/2` 约束**（与 height 无关）：平面 300×60 mm
   的侧板最多 30 mm 圆角，写 40 mm 会被服务端打回；宽 300、窄边只有 12 mm 的镜片则最多 6 mm。
   要更圆的角只能加大平面尺寸或用 `prism` 画轮廓。
10. **`prism` 的拉伸以局部 z=0 为中心**（从 −h/2 到 +h/2）。要用 `rotate:[90,0,0]` 把侧面轮廓
    （x,z）沿 y 拉伸时，`translate.y` 得给**区间中点**，给起点会整体偏掉半个厚度 —— 这个错会表现成
   「侧板跑到另一条履带那侧」，很难一眼看出。
11. **上车梯是「斜梯」，一根管子一根管子摆是摆不出来的**：真机是 55° 斜梁 + 一级级**水平**踏板 +
    两侧扶手。把它参数化成两个端点：底 (x0, z0)、顶 (x1, z1)，斜长 `hypot(run, rise)`，
    绕 +y 的倾角 `atan2(run, rise)` 直接就是 `rotate[1]`。踏板**不要旋转**（人踩的是水平面），
    靠 `linear` 阵列的 `step: [Δx, 0, Δz]` 沿斜向排，Δx=run/(n+1)、Δz=rise/(n+1)。
    扶手与斜梁平行、抬 0.9 m，末端加一根横向连成「∩」；立柱 3 根一把撑住。
    三个必须校验的量：① 整架落在**履带后端之后**（x<−2.5），否则侧视图里斜梁和履带叠在一起；
    ② 底端 **z≈0**（斜梁被转过 35° 后截面半厚会让最低点沉 −0.017 m，`z0` 要抬 18 mm 才贴地）；
    ③ 梯面法向朝 y（两根斜梁沿 y 间隔），写成「沿 y 的立杆」整架就侧对着车体、只剩一根杆。

新增一份模型的做法（不需要写建模代码）：

1. 让 AI 用 `addSolid` 拼出你要的东西，或直接照现有 JSON 改；
2. 存成 `shared/models/<id>.json`，字段就是 `id / name / summary / features`（可再加 `params` + `bindings`）；
3. 在 `shared/library.js` 的导入清单里加一行（注册，不是建模逻辑）；
4. 跑 `npm test`：`template-test` 会把每份文档按真实链路落库求值，`parametric-test` 会检查绑定表自洽。

`scripts/template-test.ts` 会把每份文档都走一遍 `applyOps`（`library`）→ `buildElementModel`，
断言「能落库 / 有面 / 特征数在**分层**上限内（总数 96、group 子特征 48、嵌套 2 层）/ 尺寸合理 /
亭子与履带吊底面贴地」，再加上各案例的专项断言（柱数、瓦片、翼角、履带镜像、臂是锥形箱型节、臂仰角、双液压缸…）——
模型库是「点一下就落到模型里」的东西，坏了比 AI 写错更难发现，所以挂在 `npm test` 里。

### 参数化：参数表和绑定表也是数据

模型文档可以带一层参数（都在 JSON 里，没有生成器）：

```json
{ "params": [
    { "key": "width", "label": "宽", "unit": "length", "min": 0.04, "max": 2, "default": 0.16, "step": 0.005 } ],
  "bindings": {
    "f1.width": "width",
    "f3.translate.0": "-(width / 2 - 0.022)" } }
```

- `params`：参数表（范围 / 默认值 / 步长），界面的「尺寸驱动」卡直接由它生成；
- `bindings`：参数 → 特征字段的表达式。只引用参数与常数，所以一次算完，不需要拓扑排序。

求值就是「深拷贝特征树 → 逐条绑定写回字段」，所有模型共用这一条代码路径。
实测 L 型支架（4 参数 / 20 条绑定）：宽 0.16 → 0.3，外廓变宽、孔位按 `-(width/2 − 0.022)` 自动外移、
立板随板厚贴边；`param.width` 还能再被公式驱动（`{"param.width": "0.2"}`）。

三个取舍：

- **快照 + 重建双写**：参数化构件仍落一份特征树快照，导出 / 明细 / `describeFeature` 读同一份结构；
  求值优先按参数重建，所以快照旧了也不影响几何（测试里把快照清空仍能出图）。
- **不让 AI 直接改参数化构件的特征**：`addFeature` / `editFeature` / `deleteFeature` 会明确报错并指路
  `setParams`。否则下一次重建会把改动吞掉，「改了没生效」是最难查的一类问题。
- **复杂模型不强行参数化**。亭子的瓦列数、24 站屋面曲线、1,512 片瓦的铺位不是几个标量能表达的；
  硬塞三个参数只会得到「改了柱高、屋顶不动」的半联动，比没有参数更坏。这类模型就存成静态特征树，
  要联动用下一节的 `setConstraints` 写关系（`f2.height = 层高 - 0.3` 这类尺寸链才是它擅长的）。

边界：只有带 `params` + `bindings` 的文档才是参数化构件（当前是 `bracket`）；
`setParams` 对静态树会明确报错并指路 `editFeature`。参数只存数字，跨特征依赖交给 `constraints`。

### 通用约束：任意模型，AI 自己定义关系

参数化的绑定表是「模型作者事先写好的关系」。真实场景里用户往往希望**关系后加**：
「柱高跟着层高走」「踏步数按层高算」「这排柱一样高」「檐口别超过 4 m」。
这些都不该要求先有模板，所以约束被做成独立的一层，挂在任何造型构件上。

```json
{ "op": "setConstraints", "target": "试验亭",
  "dimensions": [{ "name": "柱高", "path": "f2.height" },
                 { "name": "宝顶标高", "path": "f3.translate.2" }],
  "formulas": { "柱高": "层高 - 0.3", "宝顶标高": "柱高 + 0.5" },
  "checks": [{ "expr": "柱高 >= 2.2", "message": "柱高不足 2.2 m，亭下站不直" }] }
```

三个字段对应三种东西：

| 字段 | 语义 | 求值 |
| --- | --- | --- |
| `dimensions` | 给尺寸起名（别名 → 路径） | 只为可读性，不参与计算 |
| `formulas` | **驱动式**：这个数 = 表达式 | 按依赖拓扑排序，一次算完写回 |
| `checks` | **校验式**：写「要求」，为假即违规 | 算完再核对，只报告、不改模型 |

尺寸路径的语法（特征序号从 1 起，与上下文 `solid.features[].index` 一致）：

```
f2.height  f2.width  f2.radius  f2.thickness  f2.rx …      形状字段（按 shape 的字段名）
f3.count  f2.step.0/1/2  f2.patternAngle                   阵列：数量、步距、总角
f2.translate.0/1/2  f2.rotate.0/1/2  f2.scale               变换
f5.fillet  f5.shell  f5.offset                              曲面修饰的标量
f2.sections.0.ellipse.rx  f2.sections.3.airfoil.chord       放样截面（机身、机翼）
f3.g1.height                                                子特征组里的第 1 个特征
param.width                                                 模型参数（带 params 的模型才有，例如 bracket.width）
primitive.width                                             基本体尺寸
```

表达式支持 `+ - * / % ^`、比较与逻辑、`abs min max round floor ceil trunc sqrt pow exp log sin cos tan asin acos atan clamp if mod`，
以及项目参数名（`层高`、`标准层高`…）、同构件内的别名、任意尺寸路径。

**为什么不是约束求解器。** 通用几何约束（相切、同心、共线、双向拖动、过约束诊断）需要
B-rep 级别的拓扑命名 + 雅可比 + 牛顿迭代，而且和「特征树每次改参数都重建几何」天然冲突
（重建后拓扑引用就失效）。这里做的是工程上真正撑得住的那一层：**特征字段上的有向依赖图**。
单向、无环、一次拓扑排序就收敛，不需要迭代；不需要解方程；模型改一个源参数，派生量全部重算。
建筑与产品建模里 90% 的「约束」本来就是尺寸链，属于这一类。剩下 10% 明确留白，见 `docs/CONSTRAINTS.md`。

服务端把三类错误挡在落库之前，并给出可操作的提示（AI 最常犯的是编一个不存在的尺寸名）：

- 别名指向不存在的尺寸 → 报错并列出可用路径；
- 公式引用了不存在的量 → 报错并提示「先写进 dimensions」；
- 成环（甲 = 乙 − 0.5 且 乙 = 甲 + 0.5）→ 报错，要求打破环；
- 别名与项目参数同名 → 报错（会遮蔽项目参数）；
- 一个尺寸被两条公式驱动 → 报错。

**特征序号会漂移。** 插入/删除特征后，`f3.height` 会悄悄指向别的零件——这类错不报错、只是结果不对，
最贵。所以 `addFeature` / `deleteFeature` 会把约束里的路径、公式键、表达式引用一并重排
（`rebaseConstraints`），特征被删掉时相关约束直接清掉。

实测（`npm run constraint`，`diagnostics/constraints/stair-height.png`）：一棵手写的楼梯特征树
（踏步阵列 + 立柱阵列，没有任何模板），加 8 条约束后只改「层高」：

| 层高 | 踏步数 | 踏步高 | 外廓高 | 水平投影 |
| --- | --- | --- | --- | --- |
| 2.8 m | 17 | 158 mm | 3.58 m | 4.76 m |
| 3.3 m | 20 | 159 mm | 4.08 m | 5.60 m |
| 3.9 m | 24 | 158 mm | 4.68 m | 6.72 m |

踏步数、踏步高、阵列步距、立柱数量与起点高度全部由公式算出，校验式把踏步高锁在 140–180 mm
（强行改成 220 mm 只报警，不改模型）。约束定义本身 700 B 出头，几何一个字节都不用复制。

### 安全边界（`server/ai/solid.js`）

- 形状白名单：未知形状直接 400，不会静默生成一个错的东西
- 尺寸 1 mm ~ 500 m；坐标 ≤ 20 km；角度 ≤ 3600°
- 单实体特征 ≤ 96、子组嵌套 ≤ 2 层、分段 ≤ 64、轮廓点 ≤ 192、凸包点 ≤ 64、阵列 ≤ 192
- 倒圆半径 ≤ min(width, depth)/2：只受这两条平面边约束，**height（板厚）不参与** ——
  6 mm 厚、300×300 的顶盖可以放心用 20 mm 圆角；反过来说 12 mm 窄的镜片最多只有 6 mm，
  窄边窄就只能是更小的圆角（上限小于 1 mm 时直接报错，提示改用 box）、
  管壁厚必须小于外半径、凸包至少 4 点
- 首个特征必须是 `add`（先有材料才能切除）；基础特征不可删；形状类型不可原地改
- `validateDocument` 再兜一层：特征树为空或超 96 个特征直接拒绝入库

### 生成阶段预校验与自动修正（`server/ai/repair.js`）

模型偶尔会写出越界尺寸（典型：给 6 mm 薄的顶盖写 20 mm 倒圆）。只在 `apply` 校验的话，
用户体验是「生成成功 → 点应用到模型 → 报错 → 自己把错误贴回聊天框 → 模型反问一句尺寸」，
一次就能改好的事变成三轮对话。所以 `plan` / `plan/stream` 在返回前先 dry-run 一次 `applyOps`
（纯内存，不写库、不建几何，几十微秒）：

- 通过 → 返回 `repaired: 0`；
- 不通过 → 把错误原文作为【服务端校验反馈】回灌给模型，让它自己改一轮（只改 1 轮，避免烧 token）；
  改对了返回 `repaired: 1`，面板显示「已自动修正参数」；
- 还是不通过 → 保留这次的指令但带 `warning`，面板禁用「应用到模型」并给一个「让 AI 修正」按钮。

`apply` 阶段失败（例如文档刚被协作者改过）时，错误条里同样出现「让 AI 修正」按钮，
把错误原文一键交回模型，不用手动复制粘贴。

### 容错（真实模型实测踩到的）

模型经常「差不多对」，服务端因此接受几种等价写法，而不是直接 400：

- 判别字段：`op` 缺失时认 `action` / `type` / `kind` / `command`，再不行按字段签名推断
  （有 `features` → `addSolid`；有 `points`/`rect` → `addSlab` …）
- 形状写法：`shape: 'box'` 平铺 与 `shape: { shape: 'box' }` 嵌套都接受
- 位置写法：`[x, y]` 与 `[x, y, z]` 都接受
- `editFeature.patch` 既可写 `{ width: 0.3 }`，也可写 `{ shape: { width: 0.3 } }`

其余变量：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `STRU_AI_PROVIDER` | `mock` | `mock` / `openai` |
| `STRU_AI_BASE_URL` | `https://api.openai.com/v1` | OpenAI 兼容地址（不要带 `/chat/completions`） |

> 界面保存的设置优先于环境变量；环境变量仅作为默认值/兜底。

## 安全与一致性

- **权限**：`plan` 需要项目读权限；`apply` 需要写权限（`viewer` 会被 403 拒绝）。
- **校验**：`server/ai/ops.js` 校验指令形状、坐标范围、标高/类型/构件是否存在、墙长/板轮廓；
  应用后再跑一次 `validateDocument`，任何一步失败都不写库。
- **可追溯**：写入新 `rev`，审计记录 `ai.plan` / `ai.apply`；版本快照可回滚。
- **并发**：AI 应用基于当前最新文档计算并保存为新 rev，同时向协作房间广播，其他成员实时同步。
- **撤销**：前端在应用前把旧文档压入撤销栈，`Ctrl/Cmd+Z` 可回退（协作在线时会作为补丁同步）。

## 已知限制与下一步

- Mock 仅按关键词匹配（房间/墙/柱/厚度/删除），用于演示与测试；真实理解依赖配置的模型。
- token 数是按字符特征估算的（CJK 1 字≈1 token、拉丁 3.4 字符≈1 token），不是分词器精确计数；
  估算刻意偏大一点，宁可少塞也不撞网关长度上限。换用私有模型时建议在 AI 设置里显式填窗口。
- 会话摘要是**单层滚动摘要**：每次把「上一版摘要 + 新一段」重压一版，长到几百轮后摘要会逼近 1800 字上限；
  还没做分层摘要树（把早期摘要再摘要成更高层）。
- 自动压缩在响应之后后台跑：本次请求用的仍是压缩前的历史（预算会先裁到窗口以内，不会报错）；
  想让某次请求立刻用上压缩结果，点一下「压缩」即可。
- 单张照片只能做体量近似——背面和内部结构是模型推测的，尺寸靠比例估算（视觉规格里会标 `uncertain`）；
  有多视角（正/侧/顶）时一起传，识别率明显更高。
- 视口截图回灌只对「能读图」的模型生效；纯文本模型仍然只能靠特征树与材质参数判读
  （它请求的视角巡检会被跳过，并提示去启用视觉模型）。
- 自检闭环最多 5 步（一轮最多 4 个角度）：跑到上限还没收敛就停，回一句「继续」可以接着改。
  步数是硬上限——模型有时会「越看越想改」，没有上限会一直烧 token。
- 闭环的质量取决于模型能不能真的「看图判断」。视觉能力弱的模型容易看一眼就 `done`，或者在同一个地方反复改；
  前端会在**第一轮改完就自称完成**时补拍一组默认视角，但它看图后仍然判断不出问题，就只能靠人兜。
- 还没做：「平面图 → 墙线/房间」的专用提取（现在走同一套特征树，偏“体量”而不是“施工图”）；
  照片贴图 / 材质采样（图生 3D）也还没接。
- 参数化只覆盖模型文档里带 `params` + `bindings` 的那几份（当前是支架）。**任意特征树的可调性由约束层解决**
  （见「通用约束」）；两者不重叠：绑定表能连带派生字段一起重算，约束层只能驱动特征字段本身。
- 约束是单向的：改派生尺寸会在下一次重算时被覆盖（与 Revit 公式参数一致）。
  反向反解（拖派生量反推源参数）需要单变量求解，没做。
- 约束不做几何约束：相切 / 同心 / 共线 / 对称需要 B-rep 拓扑命名 + 数值求解，
  与「特征树每次重建」冲突，明确留白（`docs/CONSTRAINTS.md` 有取舍说明）。
- 校验式只报告不夹取：违反设计规则的模型照样生成，问题进面板与报告。
