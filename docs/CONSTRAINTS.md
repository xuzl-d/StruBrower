# 通用约束：任意模型上的尺寸依赖与设计规则

> 目标：不只是预置模板能调尺寸，而是**任意模型**都能由 AI 自定义「谁决定谁」和「什么不允许」，
> 改一个源参数，整组尺寸重算；违反设计规则时报警而不是偷偷改模型。

## 1. 先把「约束」拆开：三种东西，只有一种值得做成通用层

| 类别 | 例子 | 求解方式 | 是否通用化 |
| --- | --- | --- | --- |
| 几何约束 | 这两条边相切、三个孔同心、这段与那段共线 | 非线性方程组 + 牛顿迭代 + 雅可比；需要稳定的面/边/点引用 | **不做** |
| 尺寸链（驱动式） | 柱高 = 层高 − 0.3；踏步数 = round((层高 − 板厚) / 0.16) | 有向无环图上的一次拓扑求值，显式解 | 做成通用层 |
| 设计规则（校验式） | 踏步高 140–180 mm；檐口不得高于 4 m | 求值后断言，不参与求解 | 做成通用层 |

为什么不做第一类，理由不是「做不了」，而是**在这个建模内核里做不对**：

1. **拓扑命名（persistent naming）**：改一个尺寸后几何重建，第 137 号面可能变成第 214 号面。
   要让「相切于面 137」在改尺寸后仍然成立，需要一整套命名与匹配机制——这是 CAD 内核里
   出名贵的部分。
2. **需要数值求解**：欠约束时要有最小改动解（最小二乘）、过约束时要做冲突诊断，
   还得处理奇异雅可比。一次拖动要迭代十几轮，和「参数变了就重建整棵树」的即时反馈打架。
3. **表达粒度不匹配**：我们的几何是特征树的求值结果，不是可编辑的 B-rep。约束挂在拓扑上，
   等于把唯一的真相源从「特征参数」搬到「几何」，整套文档模型都要推翻重做。

而尺寸链恰好反过来：它天然是**特征字段之间的显式赋值**，单向、无环、一次算完就收敛，
不需要迭代、不需要解方程，也不碰拓扑。工程上 90% 的「约束」需求是这一类。

## 2. 三层数据模型

```
尺寸路径（path）       f2.height / f2.translate.1 / f2.sections.0.ellipse.rx / param.height
   ↑ 起名
别名（alias）          柱高 → f2.height
   ↑ 引用
驱动式（formulas）     柱高 = 层高 - 0.3
校验式（checks）       柱高 >= 2.2（为假即违规）
```

### 2.1 尺寸路径：让任意字段可寻址

这是地基。没有它，「给任意模型加约束」无从谈起——模型得先能指着一个数说话。
路径语法与实现见 `shared/dimensions.js`：

```
f<序号>.<字段>                 f2.height、f2.radius、f2.thickness
f<序号>.<字段>.<下标>          f2.translate.2、f2.step.1、f2.sections.0.ellipse.rx
f<序号>.count / step.* / patternAngle    阵列的数量、步距、总角
f<序号>.fillet / shell / offset          曲面修饰的标量
f<序号>.g<序号>.<字段>         f3.g1.height（子特征组，最多两层）
param.<key>                   模型参数（模型文档 params 里的键）
primitive.<key>               基本体尺寸
```

要点：

- **文档里的尺寸是嵌套的，对外只暴露短路径**。`f2.height` 内部翻译成 `feature.shape.height`，
  这层翻译（`fieldPath`）读写共用，否则必然出现「能读不能写」。
- **枚举与读写必须同源**。`listDimensions` 决定 AI/面板看到什么，`readDimension` / `writeDimension`
  决定算出来的东西落到哪。三者用同一张字段表，避免「列表里有、写进去没反应」。
- **写回是纯数据、不可变**。几何在下次求值时重建，因此约束引擎不需要知道渲染层存在。

### 2.2 别名：可读性 + AI 的落点

公式里当然可以直接写 `f3.translate.2 + 0.5`，但没人愿意维护那个。别名把路径映射成人话，
顺带成为服务端校验的抓手：AI 编一个不存在的名字时，能立刻指出来。

别名与路径是**双键**，面板读写公式时必须用同一个键（`formulaKeyFor`），
否则会出现「表里写了一条、引擎又读到一条」→ 同一尺寸被两条公式驱动。

### 2.3 驱动式：单向赋值

存 `element.formulas`（键 = 别名或路径，值 = 表达式）。求值：

```ts
// 1. 枚举尺寸 → 值表
// 2. 别名 → 路径
// 3. 每个公式键解析成路径；键既非别名也非路径 → 报错
// 4. 依赖只算「另一个被公式驱动的尺寸」——引用普通尺寸/项目参数不产生排序约束
// 5. 深搜拓扑排序，顺带找环（环上的键保留原值并报错）
// 6. 按序求值：变量 = 项目参数 + 上下文变量 + 全部尺寸路径 + 全部别名当前值
// 7. 结果按尺寸规格夹紧（越界夹到 min/max、整数取整），有变化才写回
```

复杂度：O(公式数 + 依赖边数)，一次遍历收敛——**不做迭代**。这一点很重要：
迭代意味着「公式互相追着改」，那是求解器，不是参数化。

### 2.4 校验式：只报告

`checks[].expr` 写的是**要求**，表达式结果为 0 即违规：

```json
{ "expr": "踏步高 <= 0.18", "message": "踏步高大于 180 mm，上楼吃力", "severity": "warn" }
```

为什么不做成「自动夹回合法区间」：那会让用户改一个数、别处莫名变了，且没有痕迹。
校验式的价值是**暴露设计问题**（面板红标、明细表、AI 上下文），不是替用户做决定。
想要自动收敛的，就把它写成驱动式。

## 3. AI 接口

一条指令 `setConstraints`，三个字段可以一次全给：

```json
{ "op": "setConstraints", "target": "试验亭",
  "dimensions": [{ "name": "柱高", "path": "f2.height" }],
  "formulas": { "柱高": "层高 - 0.3", "f3.translate.2": "柱高 + 0.5" },
  "checks": [{ "expr": "柱高 >= 2.2", "message": "柱高不足 2.2 m" }],
  "replace": false }
```

- `dimensions` 给了就**整体替换**别名表；`checks` 给了就整体替换校验规则；
  `formulas` 是**合并**，值写 `null` 表示删除这一条；`replace: true` 三者先清空。
- 上下文里会回灌 `solid.constraints = { dimensions:[{name,path,value}], formulas, checks }`，
  AI 才能看见「这个构件已经有哪些名字、哪些数被谁决定」。

校验策略（`server/ai/constraints.js`）——错误信息必须能让模型自己改对：

| 情形 | 处理 |
| --- | --- |
| 别名指向不存在的尺寸 | 400，并列出前 14 个可用路径 |
| 公式键既非别名也非路径 | 400，提示「先写 dimensions 起名，或直接用路径」 |
| 表达式引用不存在的量 | 400，点名那个量并给出两种修法 |
| 成环 | 400，提示打破环（改成字面值或改成校验式） |
| 别名与项目参数同名 | 400（否则会遮蔽项目参数，公式语义悄悄变了） |
| 一个尺寸被两条公式驱动 | 400 |
| 校验表达式语法错 | 400 |

实现上先用「探针变量」把所有尺寸与别名填 0 跑一遍语法与引用，再组装候选构件跑一次
`resolveConstraints(dryRun)` 只为了查环——这是唯一需要真算一遍才能发现的问题。

## 4. 四个工程坑（踩过才知道）

1. **特征序号会漂移**。`f2.height` 在插入一个特征后指向了别的零件，不报错、只是结果不对。
   这类错最贵。所以特征增删时把约束里的路径、公式键、表达式里的引用一并重排
   （`rebaseConstraints`），被删特征上的约束直接清掉。
2. **别名与路径双键**。面板按路径列参数，公式可以写在别名上；两边不一致就重复驱动。
3. **参数化构件只暴露 `param.*`**。它的几何由生成器按参数重建，写 `f*.height` 下一次重建就没了。
   与其让 AI 白改一次，不如在枚举阶段就不给它这个选项。
4. **收不到收敛**。驱动式必须一次算完；如果允许「算完再算」，就必须证明收敛，否则抖动。
   所以：环直接报错，不做不动点迭代。

## 5. 与既有 BIM 语义的对照

Revit 里「公式参数是只读的」不是缺陷，是刻意的：它把参数化限定为**单向**，
从而保证任何一次重算都有唯一结果，也让协作端能只交换「driver 的变化」而不交换派生值。
我们沿用同一套语义：被公式驱动的尺寸不可直接编辑，改源参数才会联动。
反向操作（拖派生尺寸反推源参数）属于求解器范畴，见第 6 节。

## 6. 边界与后续扩展

| 现在能做的 | 现在不能做的（以及要补什么） |
| --- | --- |
| 特征字段级驱动（尺寸、阵列、修饰、截面、变换） | 边/面/点级几何约束（需要 persistent naming + 求解器） |
| 单向驱动：改源参数 → 派生量重算 | 双向反解：改派生量反推源参数（需要单变量反解 + driver 声明） |
| 等式链的循环检测 | 过约束/欠约束诊断（需要秩分析） |
| 逐构件的校验规则 | 跨构件的规则集（「所有门宽 ≥ 0.9」需要选择器 + 批量求值） |
| 预置模板参数与自由特征树统一寻址 | 阵列/布尔产生的**新实例**单独寻址（如第 3 个阵列件的孔径） |

按投入产出排序，下一步值得做的是：

1. **跨构件的规则集**：现有 `element.formulas` 已能跨构件读全局参数，缺的是「对一类构件批量施加」。
2. **单变量反解**：用户拖一个派生尺寸时，沿公式链找到唯一可解的自由变量，数值二分即可（需单调性检查）。
3. **选择器 + 规则模板**：把「所有外墙」「这一层的柱」做成可复用的约束目标，AI 才能表达「全楼这套规则」。

## 7. 换一个内核时要改哪几处（复用清单）

这套东西与 three.js 无关，只依赖「模型可被分解成字段」这一前提：

1. `shared/formula.js` —— 词法 + 求值，无副作用，可直接复用；
2. `shared/dimensions.js` —— 换成新内核的字段表与路径翻译（**唯一需要重写的部分**）；
3. `shared/constraints.js` —— 求解（拓扑序 + 环检测 + 断言），与内核无关；
4. `server/ai/constraints.js` —— 把错误文案翻译成「模型能照着改」的提示，与内核无关；
5. 文档 schema：`formulas`（键→表达式）+ `constraints.{dimensions,checks}`，三个字段即可。
